# 出门啦 · 产品设计说明

## 问题与目标

针对题目中的大学生周末场景：活动信息分散，选择受预算、天气与同行人数影响；找到活动后，还需要把时间、费用与同行安排落到一份计划里。这是依据题目提出的设计假设，未开展独立用户调研，也没有已验证的用户规模或业务效果。

目标体验：**描述想法 → 找到活动 → 安排行程 → 邀请同行 → 打卡 → 分享经验。**

## 产品结构

| 页面 / 模块 | 用户决策 | 设计落点 |
| --- | --- | --- |
| 发现周末 | 选什么、为什么适合 | 常用表达解析、三城筛选、天气预报与情景切换、推荐理由 |
| 我的周末 | 什么时候走、花多少钱 | 时间轴、顺序调整、活动与餐饮交通总预算、冲突提醒 |
| 找个搭子 | 约谁、在哪里见 | 明确日期、集合点、人数与说明；本机报名演示、邀请卡 |
| 我的足迹 | 留下什么 | 文字、心情和可选照片，保存在本机 |
| 灵感攻略 | 如何让别人复用 | 编辑与分享攻略；行程链接先预览，再主动载入 |

## 核心设计选择

**先降低选择成本，再提高可执行性。** 一句话入口识别常用条件，筛选控件提供修正入口。推荐解释直接展示预算、天气或同行人数的匹配理由；用户随后可把活动排进时间轴，而非停留在活动列表。

**同时说明单项费用与全天花费。** 发现页按人均活动预算筛选，计划页把活动、餐饮预留和交通预留合计，再计算同行总额。超预算时指出差额，由用户决定删减或调整，不把活动门票当作完整出游成本。

**天气变化保留选择权。** 联网预报成功才展示来源与获取时间；限流、离线或超出预报范围时提供明确状态和手动情景。计划含户外活动时，雨天提示用户确认替换，随后重算费用和时间。

**让分享可打开，让覆盖可预期。** 行程链接保存内容快照，接收者先预览，再选择载入；本机原计划会被替换的后果在操作前说明。攻略和邀请也可分享，但不伪装成实时多人协作。记录可导出 JSON，恢复前确认覆盖并清理不合法内容。

**用可解释估算控制范围。** 转场暂按 25 分钟，演出最早排到 19:00；这些规则不验证真实交通、营业或演出时刻。日历和文字导出的是个人计划，不代表预约成功。视觉采用自然绿、留白和场景配图，兼顾手机操作与键盘访问。

## 验证与下一步

单元测试覆盖解析、预算、排程、日历、分享数据、天气错误与缓存、记录清理等关键逻辑；发布前还需分别检查桌面和手机交互、分享还原、下载与公开访问。测试通过不代表活动真实性或实际用户效果。

下一步优先接入带来源和更新时间的真实活动；补充营业时段、地图路程与用餐时间；再建设账号和共享小队状态。通过实际体验观察从筛选到加入计划、发起同行和分享的完成情况，决定后续优化重点。
