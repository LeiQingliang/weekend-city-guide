# 出门啦 · V5 产品设计说明

[产品与运营策略](PRODUCT-STRATEGY.md)补充用户任务、痛点优先级、可证伪试验、供给运营、指标和单元经济。站内“产品与运营”可切换产品判断、运营验证、商业测算；日常计划新增出发核对与具体原因反馈。运营计数仅为本机操作，商业参数均为待验证假设。

## 从题目出发

大学生周末需要的不只是更多活动，还要回答：哪个适合自己、一天准备多少钱、时间够不够、天气变了怎么办、朋友能不能一起走。这些是依据原题提出的设计假设，尚未开展独立用户研究，也没有已验证的用户规模或经营效果。

目标路径：**发现地点 → 比较方案 → 安排行程 → 确认同行 → 打卡与分享。** 产品重点是减少出发前的反复确认，让一个想法逐步变得具体。

## 原题如何落到产品

| 原题需求 | 当前设计 | 用户可以验证的行为 |
| --- | --- | --- |
| 根据偏好推荐本地活动 | 城市、展览/市集/演出/户外、节奏与同行人数；一句话解析、搜索与收藏 | 改兴趣会改变优先组合；独自或多人出行对同类候选排序有轻量影响 |
| 综合天气、预算 | 全天预算与单项预算分开，天气预报与手动情景分开 | 雨天排除室外；全天金额含活动、餐饮及交通预留，超限不强行给方案 |
| 减少信息分散 | 12 个真实地点的地址、来源、开放和预约信息集中在详情 | 能打开来源核对；已知闭馆日和时间冲突影响排程与方案 |
| 支持组队出发 | 创建小队 → 分享邀请 → 朋友回传参加回执 → 发起人核对并导入 | 用两个独立浏览器手动完成邀请、参加或撤回及名单变化 |
| 打卡记录、攻略分享 | 文字和照片打卡，打卡转可编辑攻略，链接与二维码分享 | 实际花费由用户补充；保存后生成攻略快照，本机记录可备份恢复 |

## 关键产品选择

**先给具体答案，再邀请用户表达。** 首页提案先交代去哪里、多久、规划人均多少。三步定制依次收集“选心情、定预算、留时间”，最多给两份不同组合，重点比较体验、总费用和时间。只有一份可行就显示一份，没有结果则解释限制并给修改入口。草稿中的选择在确认采用前不覆盖已有计划。

**硬条件约束结果，软偏好帮助取舍。** 城市、全天预算、可用时长、雨天室内条件及已知常规营业冲突共同约束方案。兴趣优先；单人更偏向灵活看展、户外，多人更偏向逛街、户外、观演，这是可解释的偏好，不是假装知道朋友性格、场地容量或余票。方案说明未覆盖的兴趣、少一站或费用更高等取舍，并显示按人数计算的同行规划总额。

**完整费用要先定义口径。** 定制和计划页合计活动、餐饮与交通预留；活动列表筛选的是单项金额。官方明确免费、未核实的门票预留、可选购物消费分别记录。用户查到价格后可修改某站金额，整趟预算与导出同步重算；新定制回到目录预留，避免把旧计划的金额套在新方案上。预算约束基于这些规划金额，不保证实际票价和消费；餐饮目前只预留费用，尚未排入用餐时段。

**把地图和可信信息放在选择旁边。** 列表与 Leaflet 地图共享选中地点，11 个已核对的 OSM 点位帮助比较相对位置；区域参考点和具体场馆有明确区分。徐汇滨江没有可靠匹配坐标，保留文字与列表。底图加载失败时保留地点操作，提供重试和高德地点搜索，不以空白地图阻断选择。地图不推算路线或转场时间。

**时间不能只做加法。** 西岸美术馆、浙江美术馆和 UCCA 已录入有来源的常规开放时间、闭馆日及最后入场限制。提前到达安排等待，等待计入整趟时长；定制及雨天替代排除已知不可行的安排，手动计划保留用户选择并提示冲突。节假日和临时调整仍需查官方。转场目前统一预留 25 分钟，演出暂按 19:00 后估排，实际场次未确认。

**让天气变化可处理、让替换可确认。** 成功取得预报才标记联网来源；限流、断网和超出范围均有提示，并可切到天气情景。雨天替代保留已选室内活动，在预算、时长与已知营业约束内寻找替换；必要时减少室外站点，没有可行安排则保留原计划。用户先看新的费用和时间，再确认替换。

**组队落在一次明确的确认动作上。** 发起人创建小队并自行分享邀请。朋友打开链接、填写昵称、生成参加回执，使用已有聊天把链接发回；发起人预览变更并确认，名单才写入本机。撤回也通过新回执传递，重复和旧版本不会重复增加人数。这样能跨浏览器传递意向，但不提供实时共享状态、身份认证或自动消息；示例小队只用于展示，不能当成真实报名。人数上限是发起人的小队约定，不是场馆库存。

**把出发后的记录变成下一次参考。** 打卡可以整理成攻略草稿，保留用户文字、地点和交通线索，实际花费留待补充；修改并保存后再分享。链接预览、覆盖确认、备份恢复贯穿记录流程。90 秒导览使用隔离的临时记录，退出还原进入前状态，刷新重新载入原有记录；已发出的链接不会被撤回。

## 当前范围与下一步

应用推荐、需求解析、排程及记录在本地运行，未调用大模型。AI Coding 参与需求拆解、设计、实现与检查，过程说明见 [体验指南](SHOWCASE.md)；视觉与交互参照见 [设计依据](DESIGN.md)。

下一步优先补足有维护机制的真实展览、演出和市集场次、实际票价、路程与用餐时段，再评估有账号的小队共享状态。验证重点是用户能否完成选择、理解费用口径、处理天气变化并确认同行；实际检查证据单独记录在 [验证记录](VERIFICATION.md)，不以检查数量代替产品效果。
